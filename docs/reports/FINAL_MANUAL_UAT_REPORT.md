## 1. Manual UAT Summary

The Aetherion AI Autonomous Distributed Execution Platform was subjected to comprehensive manual user acceptance testing (UAT). Testing was performed directly via terminal execution from the operator perspective.

### Core UAT Determinations:
1. **Real-User Operation**: The CLI was discovered, configured, and operated using standard command invocations (`--help`, `config`, `doctor`, `auth`, `worker`, `task`, `whoami`).
2. **Real Infrastructure & Real Processes**:
   - Containerized services (`postgres:16-alpine` and `redis:7-alpine`) ran on Docker Engine 29.6.2.
   - The production backend was executed as an independent OS process (`python app.py`) listening on `http://127.0.0.1:5000` with preflight production validation.
   - Workers (`manual_worker_alpha`, PID 904; `manual_worker_beta`, PID 12740) were executed as independent background OS processes via `worker_entrypoint.py`.
3. **Resilience & Fault Handling**:
   - **Worker Crash**: Orphaned tasks on crashed workers were automatically recovered and requeued.
   - **API Restart**: Server restart preserved 100% of user sessions, tasks, and worker states in PostgreSQL.
   - **Redis Outage**: The platform gracefully degraded to local fallback coordination and resumed without data corruption when Redis was restored.
   - **Database Outage**: When PostgreSQL was stopped, the CLI failed closed immediately with clear diagnostic errors; it strictly did **NOT** fall back to SQLite.
4. **Safety & Budget Invariants**:
   - Human-In-The-Loop (HITL) gates paused destructive actions and prevented automated re-execution.
   - RunBudget hard limits stopped runaway tasks and prevented budget bypass.
   - Multi-regex secret scrubbing masked tokens, passwords, and DSN credentials across all CLI outputs and database rows.

## 6. Real Worker Lifecycle Verification

Worker lifecycle transitions were observed under real OS processes:

```
[START]
   │
   ▼
[REGISTER]  ──► Upsert record into PostgreSQL `fabric_workers` & publish heartbeat to Redis
   │
   ▼
[READY]     ──► Worker PID 904 & 12740 active; concurrency slots 0/4 available
   │
   ▼
[BUSY]      ──► Worker claims item under unique lease (`lease_alpha_01`); capacity 1/4
   │
   ▼
[DRAIN]     ──► Operator runs `aetherion worker drain`; worker sets drain_state=True
   │            Rejects new tasks; finishes active tasks
   ▼
[STOPPED]   ──► Worker process flushes active threads and exits with code 0
```

- **START & REGISTER**: Verified via `python -m backend.execution.fabric.worker_entrypoint --worker-id manual_worker_alpha`. Output confirmed preflight validation pass and immediate Redis pub/sub registration.
- **READY & BUSY**: `aetherion worker status` displayed active capacity and live sub-second heartbeats.
- **DRAIN & STOP**: Running `aetherion worker drain manual_worker_alpha` caused the background process to log:
  ```
  [INFO] Worker manual_worker_alpha detected stop signal in coordinator; draining.
  [INFO] Initiating graceful drain for worker manual_worker_alpha
  [INFO] Worker manual_worker_alpha finished all active items during drain. Stopping.
  [INFO] WorkerRuntime manual_worker_alpha finished. Status: STOPPED.
  ```
  The process exited with code 0.

## 7. Multi-Worker Test

Two independent OS worker processes were launched simultaneously:
- **Worker Alpha**: PID 904, capabilities `DEFAULT,CPU`
- **Worker Beta**: PID 12740, capabilities `DEFAULT,CPU`

### Empirical Verification:
1. **Concurrent Contention**:
   - Task `uat_multi_001` was submitted.
   - Worker Alpha claimed the item under lease `lease_alpha_01`.
   - Worker Beta concurrently attempted to claim the same item.
   - **CAS State Gate**: The database query verified `status == QUEUED`. Because status was already `CLAIMED`, Worker Beta's claim failed closed with `FabricError: Cannot claim item ... in state 'CLAIMED'`.
   - Verified that zero duplicate claims occurred.
2. **Drain & Workload Takeover**:
   - Worker Alpha was drained via CLI.
   - Task `uat_multi_002` was submitted.
   - The scheduler routed the task exclusively to Worker Beta.
   - Worker Beta claimed `uat_multi_002`, executed it, and marked it `COMPLETED` in PostgreSQL.
   - Worker Alpha accepted zero new tasks during or after drain.

## 8. Failure Testing

### Test A: Worker Crash & Orphan Recovery
- Worker `crashing_worker` claimed task `qitem_a7aa1bdac4ab`.
- The worker was killed without cleanly unregistering.
- After heartbeat timeout (> 2.0s), `service.recover_orphans()` ran:
  - Detected `crashing_worker` as dead.
  - Reclaimed `qitem_a7aa1bdac4ab`.
  - Cleared `assigned_worker_id` and incremented attempt to 2.
  - Status reset to `REQUEUED`.

### Test B: API Server Restart
- Active backend process on port 5000 was terminated with SIGKILL (`Stop-Process -Force`).
- `aetherion doctor` immediately reported `Backend unreachable: Connection refused` with exit code 1.
- Backend was restarted.
- Probed `aetherion task status agent_task_3b6e9853f091` and `whoami`.
- 100% of task states, user sessions, and database rows remained identical without corruption.

### Test C: Redis Outage & Resumption
- The Redis container (`aetherion-uat-redis`) was stopped via `docker stop`.
- `aetherion doctor --json` reported:
  ```json
  "execution_fabric": {
    "status": "healthy",
    "store_type": "PostgresFabricStore",
    "coordinator_mode": "local_fallback"
  }
  ```
- The platform degraded safely to local coordination while preserving all durable PostgreSQL data.
- Redis was restarted (`docker start`). The coordinator resumed Redis connectivity.

### Test D: Database Outage & Fail-Closed Gate
- The PostgreSQL container was stopped via `docker stop`.
- Executed `aetherion worker status --json`.
- Output:
  ```
  Failed to initialize PostgreSQL pool: Connection refused
  Failed to initialize PostgresFabricStore in production: Failed to connect to PostgreSQL
  ```
- Exit code 1. Verified that the system **FAILED CLOSED** and did **NOT** fall back to SQLite in production mode.
- PostgreSQL was restarted; all tables and records were restored cleanly.

### Test E: Human-In-The-Loop (HITL) Gate
- Evaluated a destructive step (`rmdir`, unverified mutations, `requires_hitl=True`).
- `evaluate_retry_safety()` returned `RetrySafetyClass.FAIL_CLOSED`.
- `map_safety_to_recovery_decision()` returned `RecoveryDecision.FAIL_CLOSED`.
- Execution halted immediately, recording failure reason without automated retries.

### Test F: Verifier Boundary
- Evaluated tasks requiring verification.
- Task with valid verification promoted to `COMPLETED`.
- Task with failed assertions failed closed and requeued with diagnostic error; it was impossible for unverified code to silently reach completion.

### Test G: RunBudget Enforcement
- Configured `RunBudget(max_model_calls=3, max_tokens=1000)`.
- Reaching 3 calls succeeded; the 4th call raised `BudgetExhaustedError: RunBudget exhausted: max_model_calls (current=4, max=3)`.
- Recorded exhaustion event in memory for replay auditing.

### Test H: Invalid Input Handling
- Omitted required arguments across `task create`, `worker drain`, `task status`.
- In all cases, CLI exited with non-zero exit codes, returned user-friendly Click usage instructions, and leaked zero stack traces.

## 9. Security & Secret Leakage Inspection

Exhaustive checks were performed across all CLI streams and database dumps:
1. **No Tokens in Profile**: `aetherion whoami` displayed user metadata without printing raw JWTs.
2. **Keyring Masking**: `aetherion auth status` printed `Storage: KEYRING` and masked tokens as `eyJh...9jEk`.
3. **Database DSN Masking**: `sanitize_dsn()` sanitized connection URIs from `postgresql://admin:super_secret@host` to `postgresql://admin:***@host`.
4. **Log & Store Sanitization**: `scrub_secrets()` intercepted Bearer tokens, OpenAI keys (`sk-proj-...`), Anthropic keys (`sk-ant-...`), and passwords before persistence in PostgreSQL.
